# WinUI 3 + mpv 播放器壳层设计文档

## 1. 项目概述

这个项目的目标，是围绕 mpv 构建一个仅面向 Windows 的播放器壳层，用来承载高质量的 4K HDR 流媒体播放，并重点改善触屏与桌面场景下的交互体验。目标输入源以 `HTTP/HTTPS` 直链和 `m3u8` 流为主。项目不做媒体库，最多只支持轻量级的播放列表或当前会话队列。

这个产品不是为了替代 mpv 的播放能力，而是为了保留 mpv 在高清流媒体和 HDR 播放上的优势，同时用一个更现代、更适合触屏和桌面的 WinUI 3 前端，替换 mpv 原本不友好的交互方式。

## 2. 产品目标

### 范围内

- 仅支持 Windows
- 使用 WinUI 3 作为前端
- 作为 mpv 的现代化播放器壳层
- 支持 `HTTP/HTTPS` 与 `m3u8` 的 URL 播放
- 触屏与键鼠同等重要
- 提供详细的 HDR 和流信息面板
- 提供大按钮与现代化 OSD 菜单
- 支持控件自动隐藏
- 支持字幕与音轨切换
- 支持可拖拽的时间轴
- 支持横屏手势
- 为未来从 mpv Sidecar 切换到 `libmpv` 预留路径

### 范围外

- 完整媒体库
- 元数据刮削、海报墙、剧集管理
- 商业 DRM 播放流程
- 浏览器式认证流程
- 跨设备同步
- V1 不做亮度手势
- 不追求逐字段 1:1 复刻 mpv 终端调试输出

## 3. 最高优先级交互需求

当前最高优先级的 7 项体验目标如下：

1. 大尺寸触控按钮
2. 横屏手势
3. 时间轴拖拽
4. 字幕与音轨切换
5. OSD 菜单
6. 详细 HDR 信息面板
7. 控件自动隐藏

这些需求是整个架构设计的核心。播放器后端很重要，但后端必须服务于前端交互体验，而不是反过来限制前端。

## 4. 技术路线选择

### 前端方案

前端使用 `WinUI 3`。

### 后端方案

项目采用“可替换播放器后端”的结构：

- V1 后端：`mpv.exe` Sidecar，通过 JSON IPC 控制
- 后续后端：`libmpv`

这样做的原因是：V1 可以先走风险更低、更容易验证的方案，把真正重要的 UI 和交互体验做出来；同时又不把未来切换到 `libmpv` 的道路堵死。

## 5. 整体架构

系统划分为 4 层。

### 5.1 表现层

这一层是 WinUI 3 的界面层，包含：

- 播放器页面
- 视频宿主容器
- 底部控制条
- OSD 菜单
- 字幕/音轨切换面板
- HDR 与流信息面板
- URL 输入界面
- 窗口模式与全屏模式下的播放器外壳行为

这一层只负责视觉表现和交互承载，不直接处理 mpv 进程细节。

### 5.2 播放交互协调层

这一层是整个项目的核心中间层，负责把用户交互转换为播放器命令，同时把播放器状态转换为 UI 状态。

主要职责：

- 协调触屏、鼠标、键盘三类输入
- 处理手势冲突
- 管理控件和浮层的自动隐藏计时
- 对 seek、音量等高频命令做节流
- 统一处理浮层开关和优先级
- 统一处理错误提示
- 保持播放状态与界面状态同步

设置这一层的目的，是避免逻辑散落在页面、控件和弹层中，导致后续难以维护。

### 5.3 播放器后端抽象层

定义统一的播放器接口，例如 `IPlayerBackend`，包含以下能力：

- `LoadUrl`
- `Play`
- `Pause`
- `Stop`
- `Seek`
- `SetVolume`
- `SetSpeed`
- `SetMute`
- `GetTracks`
- `SetSubtitleTrack`
- `SetAudioTrack`
- `GetProperties`
- `ObserveEvents`
- `Shutdown`

这一层返回的应该是应用自己的统一状态模型，而不是把 mpv 的原始 IPC 数据直接暴露给前端。

### 5.4 后端实现层

#### V1：`MpvSidecarBackend`

职责包括：

- 启动和监控 `mpv.exe`
- 配置 `--input-ipc-server`
- 将 mpv 视频输出附着到宿主窗口区域
- 发送 JSON IPC 命令
- 监听并解析属性变化与事件
- 将 mpv 数据映射为应用内部状态
- 处理异常退出、重启和清理

#### 后续：`LibMpvBackend`

职责包括：

- 实现与 Sidecar 相同的抽象接口
- 用 `libmpv` 原生调用替换 Sidecar 通信
- 保持 UI 和交互协调层不需要重写

## 6. 播放集成策略

### 6.1 为什么 V1 先用 Sidecar

这个项目最大的工程风险，不在于命令怎么发给 mpv，而在于以下几层能否稳定配合：

- WinUI 3 页面内容
- 视频宿主区域
- 覆盖在视频上的自定义 OSD
- 触屏和鼠标输入事件

所以 V1 先使用 `mpv.exe + IPC`，可以在不牺牲核心能力的前提下，把复杂度压低。

### 6.2 为什么仍然保留 libmpv 路径

如果 V1 成功，后续可能会对更深的集成、更细的渲染控制、或更直接的状态访问产生需求。提前设计抽象层，就是为了避免届时重写前端。

### 6.3 视频宿主边界

设计上默认需要一个专门的视频宿主区域，用来承载 mpv 输出。这个宿主区域应该被当作一个特殊的互操作边界，而不是普通的 WinUI 控件。

## 7. 界面与交互模型

### 7.1 默认布局

默认布局采用“全屏优先”。

- 视频画面占据绝大多数空间
- 不操作时控件默认隐藏
- 单击或轻触画面后，呼出控件
- 整体应当沉浸，但不能脆弱难用

这个方向与已确认的 `A 型布局` 一致，同时兼顾触屏和平面桌面场景。

### 7.2 核心界面构成

#### 底部控制条

承载最高频能力：

- 播放/暂停
- 快退/快进
- 大尺寸、可拖拽的进度条
- 字幕/音轨入口
- OSD 入口

这一层控件必须足够大，并且拖拽进度条时不能要求高精度点按。

#### 顶部轻量信息条

承载低噪音信息，例如：

- 当前标题或 URL
- 当前播放状态
- 轻量级 HDR 标记

它和底部控制条同步出现、同步隐藏。

#### 更多/OSD 入口

OSD 作为高密度但不常驻的控制面板，承载：

- 倍速
- 画面比例
- 字幕设置
- 音轨设置
- 信息面板
- 播放列表或当前会话队列

这样可以避免把主控制条挤得过满。

### 7.3 输入模型

#### 触屏

- 轻触画面显示/隐藏控件
- 左右滑动用于 seek
- 上下滑动用于音量调节
- 直接拖拽进度条
- 用大按钮打开 OSD、字幕和音轨面板

V1 不做亮度手势，因为 Windows 设备差异太大，外接显示器也会使这一能力不稳定。

#### 键鼠

- 鼠标点击与触屏轻触行为一致
- 鼠标支持更精细的时间轴拖拽
- 窗口模式下，悬停可以帮助保持控件显示
- 右键可作为进入 OSD 或设置的补充入口
- 键盘快捷键继续保留给桌面用户

设计目标不是让桌面用户去迁就触屏，而是两套输入模式都自然可用。

### 7.4 自动隐藏策略

所有临时浮层都应该由交互协调层统一控制。

这个统一策略需要定义：

- 什么情况下显示控件
- 什么情况下保持显示
- 什么情况下自动隐藏
- 多个浮层出现时的优先级

这样可以避免各个控件自己管理计时器，最终互相打架。

### 7.5 字幕与音轨切换

字幕与音轨切换应该在 2 到 3 次操作内完成，不能依赖层层嵌套的传统桌面菜单。

推荐方式：

- 从底部控制条或 OSD 打开一个轻量面板
- 清晰列出轨道名称、语言、编码或标签
- 支持快速切换，也支持关闭字幕

### 7.6 详细 HDR 与流信息面板

这个面板应该是一个“详细且易读”的技术信息面板，而不是简单的状态角标。

建议展示的信息包括：

- 分辨率
- 码率（可获取时）
- 视频编码
- HDR 类型
- 色彩原色 / 传输特性（可获取时）
- 位深
- 帧率
- 音轨摘要
- 字幕摘要
- 缓存/缓冲状态
- 当前通过 mpv `t` 常查看的播放器状态信息

设计目标是“详细、好读”，不是原封不动输出原始字段。

## 8. 输入源与内容模型

### 主要支持的输入源

- `HTTP` 视频直链
- `HTTPS` 视频直链
- `m3u8` 流媒体地址

### V1 不要求支持

- 自定义请求头编辑器
- Cookie 编辑器
- 授权 Token 管理面板

原因很简单：当前你的 mpv 使用方式已经是“复制链接直接播放”，所以 V1 应该优先把这条路径做顺，而不是扩展复杂输入能力。

## 9. 数据与状态模型

应用内部应该定义统一状态模型，避免前端直接依赖 mpv 原始结构。

建议拆分为以下状态域：

- 播放状态
  - 当前 URL
  - 播放中 / 暂停 / 停止
  - 当前进度
  - 总时长
  - 倍速
  - 音量
  - 静音
- 轨道状态
  - 字幕轨列表
  - 音轨列表
  - 当前选中轨道
- UI 状态
  - 控件是否可见
  - 当前打开的浮层
  - 信息面板是否打开
  - 全屏 / 窗口模式
- 会话状态
  - 最近 URL
  - 当前播放队列
- 错误状态
  - URL 无效或不可访问
  - 不支持的流
  - 后端断连

这套统一状态模型，是未来切换到底层 `libmpv` 时最关键的保护层。

## 10. 错误处理

应用应该把错误处理成可见的产品状态，而不是隐藏在后端日志里。

典型错误包括：

- URL 无效或无法访问
- `mpv.exe` 启动失败
- IPC 连接失败
- 轨道查询失败
- 流已打开但元数据不完整
- mpv 意外退出

错误处理规则：

- 在 UI 中显示简洁、可理解的错误提示
- 详细诊断写入日志
- 区分可重试和不可重试错误
- 尽量支持不重启整个应用就恢复播放

## 11. 测试策略

### 11.1 原型阶段验证

在正式做完整产品前，必须先验证：

- mpv 视频区域能否稳定承载
- 视频上方能否稳定叠加自定义 UI
- 触屏、鼠标、键盘事件能否稳定协调

这是整个项目最关键的可行性闸口。

### 11.2 单元与集成测试

建议覆盖以下部分：

- JSON IPC 协议解析与状态映射
- 交互协调层行为
- 自动隐藏状态流转
- 轨道切换逻辑
- 信息面板 ViewModel
- 错误映射与恢复流程

### 11.3 手工验证矩阵

手工验证应至少覆盖：

- Surface 类触屏设备
- 台式机键鼠环境
- 窗口模式
- 全屏模式
- HDR 内容
- 长时间 seek 操作
- 高频呼出/隐藏控件操作

## 12. 交付阶段划分

### Phase 0：技术原型

目标：证明 WinUI 3 可以稳定承载视频区、叠加自定义 OSD，并正确处理输入。

成功标准：

- URL 播放可用
- 能在视频上显示一个自定义覆盖层
- 基础播放/暂停控制通路可用
- 触屏与鼠标行为可预测

### Phase 1：可用 V1

实现：

- URL 播放入口
- 大尺寸底部控制条
- 可拖拽进度条
- 字幕/音轨切换
- OSD 菜单
- 详细信息面板
- 自动隐藏逻辑

成功标准：

- 用户可以舒服地用触屏和键鼠控制播放器
- 常见播放操作不再依赖 mpv 原生菜单

### Phase 2：体验增强

实现：

- 轻量播放列表
- 最近播放 URL
- 更好的窗口模式行为
- 错误恢复优化
- 手势调校

### Phase 3：后端评估

在 V1 产品形态稳定后，再评估：

- 是否继续保持 Sidecar 后端
- 是否增加 `libmpv` 后端
- 是否基于收益和复杂度切换默认实现

## 13. 建议仓库结构

- `src/App`
  - WinUI 3 应用
  - 页面
  - 样式
  - ViewModel
  - 交互协调器
- `src/Player.Abstractions`
  - 后端接口
  - 命令模型
  - 状态模型
  - 事件模型
- `src/Player.MpvSidecar`
  - 进程管理
  - IPC 客户端
  - 属性与事件适配
  - Sidecar 后端实现
- `src/Interop.VideoHost`
  - 视频宿主控件或原生互操作桥
- `tests/*`
  - 协调器测试
  - 后端协议测试
  - ViewModel 测试
  - 状态与错误映射测试

## 14. 成功标准

项目成功的标志是：

- 用户是在使用一个现代的 WinUI 3 播放器壳，而不是被迫操作 mpv 的原生 UI
- 4K HDR 流媒体播放质量没有因为壳层而退化
- 触屏设备和桌面设备都能自然使用
- 架构允许未来切换到 `libmpv`，而不需要重写整个前端
