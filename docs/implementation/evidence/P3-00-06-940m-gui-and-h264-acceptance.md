# P3-00 940M / Intel HD 4600 本机 GUI 与 H.264 验收

日期：2026-11-04。承接 [HEVC 兼容修复](P3-00-05-940m-hevc-compatibility-fix.md)。结论：**本机旧设备故障跟进在以下范围内完成，GUI 与常见 H.264 负载通过**。当前源码的旧 Intel HEVC 软件回退保留；旧候选 ZIP 未覆盖，本轮不等同于含修复的新候选最终目录验收。

## 用户确认的设备范围

用户明确：“这个设备的芯片都不支持 hevc 的硬件，就不要求硬件了，也要求不了。软解的 4k60 也不要求性能，h264 性能合理即可”。因此，本设备不再以 HEVC 必须硬解或 HEVC 4K60 吞吐作为完成条件；验证软件解码的真实画面、操作、EOF、稳定性和退出。H.264 则验证实际 D3D11 硬解和常见负载的自然播放表现。

前轮 Debug/Release 显式兼容回归各 547 通过、0 失败、2 条件跳过继续有效，192 项构建输入及素材哈希另作收尾复核。两项跳过对应 HEVC Main10 必须硬解和 TS 硬软解对照；同一素材的独立软件回退用例已执行通过。这两项硬解前提按本次用户要求不适用。原严格 runner 的 `allCommandsPassed=false`、原严格性能断言失败及崩溃材料保持原样，不倒改为通过，也没有放宽原有测试断言或修改 runner。

## H.264 性能

用已固定来源的 FFmpeg 生成本轮独立素材，参数、工具与媒体 SHA-256、ffprobe 信息均保存在记录根目录，未覆盖原来的固定素材。提前登记常见负载条件：1080p30 至少 29 fps、720p60 至少 58 fps，稳态呈现丢帧比例不超过 1%，解码丢帧为零、实际 `d3d11va`、正常退出和资源释放。

同一最终 Debug 构建的真实应用 `performance` 模式，预热 3 秒、稳态 20 秒，测量窗口内不进行像素读回或 Computer Use 截图；结束后才检查非黑画面。实际 Intel HD 4600 / 驱动 20.19.15.5171、非 WARP、调试层关闭、1382×903 SDR 表面。

| 片源 | 稳态呈现 | 呈现丢帧增量 | 解码丢帧增量 | 判定 |
|---|---:|---:|---:|---|
| H.264 1920×1080 / 30 fps | 29.9858 fps | 0 | 0 | 通过；媒体推进 20.100 秒 / 墙钟 20.039 秒 |
| H.264 1280×720 / 60 fps | 59.9993 fps | 0 | 0 | 通过 |
| H.264 1920×1080 / 60 fps（补充） | 59.0630 fps | 19，约 1.58% | 0 | 未达到补充的 1% 丢帧目标，保留限制 |

三次均实际 D3D11 硬解 / GPU 纹理，解码模式保持、退出 0、会话及渲染器释放，见 `perf-*/` 和 `h264-performance-assessment.json`。1080p30 预热前已累计 2 帧呈现丢帧，稳态增量为 0；不把预热前计数隐去。

GUI 首轮最大化 1920×991 表面并使用信息面板时，1080p60 日志约 30–33 fps，约 30 秒时呈现丢帧 902，原样保留。第三轮 Release 无 CUA 绑定的对照在 1382×903 表面也有约 49.64–59.47 fps 的分段波动，之后正常到 EOF；不能认定截图是唯一原因，也不将 1080p60 全屏/全部条件写成零丢帧通过。本次“合理 H.264 性能”的完成结论限定于已测常见负载，不要求 HEVC 软件 4K60 性能。

产品、测试和构建脚本本轮未修改；前轮修复与回归身份保留。三轮 GUI 和三个性能探针正常退出，用户最近记录按开工状态恢复，见 `history-restoration.json`。原候选包保持原哈希，本轮未发布新包、未验证 NVIDIA 940M 独显渲染路径、未扩展长期稳定性或其他硬件矩阵。

收尾输入/二进制/素材身份和进程检查见 `final-verification.json`，原始材料 SHA-256 清单为 `evidence-sha256.json`。本设备原生故障、GUI 连接与验收跟进据本次范围收口；P3-00 整体的候选更新及最终目录工作仍按 [进度](../phase-3-progress.md) 分开记录。
