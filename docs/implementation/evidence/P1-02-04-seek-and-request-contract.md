## 2. 状态与控制契约

下表描述现有状态、事件和命令组合的可观察语义；本轮没有新增一套公开播放状态枚举。加载、错误、事件丢弃补偿和终态的实现细节沿用前三份记录。

| 场景 | 状态与反馈 | 命令及迟到结果的边界 |
|---|---|---|
| 打开媒体 | 原生接受 `loadfile` 后切换地址，`StartFile` 重置媒体，`FileLoaded` 完成加载 | 提交前取消保留原媒体，提交后只取消等待；新加载（包括同地址）使旧 seek 回复失效 |
| 缓冲 | `BufferingChanged` 表达缓存暂停；结束、错误或新媒体清理旧缓冲 | 不等同于加载等待，不建立终态；积压补偿沿用前两轮 |
| 播放 | loaded、pause、idle、EOF 共同决定 `IsPlaying` | 加载后可播放；终态拒绝；取消/超时的已提交命令仍可能完成 |
| 暂停 | 实际状态由原生暂停及后端事件确认，UI 显示控制条 | 不清空媒体；异步返回仍遵守终态和释放保护 |
| 绝对 seek | 目标按已知时长限制到有效区间；未知时长时下限为 0 | 与相对 seek 共用回复顺序；旧回复不能覆盖新请求的位置或错误 |
| 相对 seek | 原生命令仍按实际相对位移发送；无新位置变化时，UI 可沿用待确认目标累计预计落点 | 预计值不是原生落点确认；期间出现实际位置变化时优先保留实际状态。依赖失败请求的预计目标见第 3 节追加场景 |
| EOF | 停止播放并显示控制条；已知时长时进度对齐末尾 | 待处理 seek 回复失效；已卸载媒体的播放/seek 按既有实现重载原地址 |
| 可恢复错误 | `Loading`、`Playback`、`EventQueue` 显示错误并清理缓冲，允许重新加载 | 错误使此前 seek 回复失效。QueueOverflow 另行尽力暂停实际 core，不能由单独迟到 `FileLoaded` 宣称恢复 |
| 不可恢复终态 | `Initialization`、`Session`、`EventStream`、`Rendering` 保留故障原因并要求重新启动 | 后端/UI 的终态保护沿用上一轮；旧命令成功、媒体事件或 seek 失败不能清除终态。渲染专用路径的声音操作例外见上一份记录 |

## 3. seek 回复顺序与预计位置

绝对定位、前后跳转和横向拖动共用 seek 版本。错误只由当前请求呈现，位置只采用仍属当前预计链的最新目标，且要求未释放、未处于终态。旧回复不能回填自己的目标、清除新失败或覆盖新成功；它只能参与确认当前预计链的依赖是否全部成功。

命令成功只表示请求确认。等待期间位置变化时保留实际位置；只有音量或暂停等非位置状态变化时仍保留待确认目标。连续相对 seek 共用预计链累计落点，例如从 20 秒连续两次 `+30` 预计到 80 秒；绝对 seek 建立独立预计链。实际 core 仍接收相对命令，不根据 UI 估计改发绝对命令。

发起新加载（包括同地址）、后端媒体地址变化、EOF、媒体错误及释放都使旧 seek 回复失效，阻止旧位置回写、旧错误污染新媒体或旧成功清除后到的播放错误。

追加红测确认：前一次 seek 等待失败后，后续相对 seek 仍显示依赖它计算的 65/80 秒，依据已不可靠。预计链因此同时记录最新目标、请求版本、位置版本、未完成依赖数和有效性；只有全部依赖成功、仍为最新请求且期间没有实际位置变化，才回填最新目标。即使后续相对请求先回复，仍需等旧依赖完成；旧依赖随后失败也会使预计链失效。

失效链等待真实位置或新的独立绝对目标，不减去失败请求的位移来猜测落点：超时不保证撤销原生命令，不能假定前一次必然执行或未执行。过时错误仍不显示，独立绝对目标和已经观察到的实际位置也不受它影响。新增回归包含“后续相对请求先成功、旧依赖再失败”的回复顺序。

当前最新请求失败时也保留无效链，避免后续相对请求重新从陈旧 UI 位置计算。前置请求成功发生在最新失败之前或之后，都等待实际位置更新；新的绝对请求可以建立独立目标。首轮全量 Debug 279 项通过后，静态复核补齐了这一边界及两项回归，最终验证使用下方的 `*-final` 记录。

## 4. 请求取消、超时及迟到回复

`RequestContractTests` 使用真实 mpv 会话和已有提交回调，以线程屏障控制排队及已提交、回复未派发的边界。

| 场景 | 验证的契约 |
|---|---|
| 排队请求取消 | 请求尚未进入原生时取消，随后读取原生音量确认没有发生修改，新请求仍可完成 |
| 紧邻提交的取消 | 事件线程即将执行下一条排队命令时取消，重复 32 次确认该边界没有改动原生音量 |
| 排队请求超时 | 等待超时后放行事件线程，已超时请求不再修改原生值，后续请求恢复 |
| 已提交请求取消，迟到成功/错误 | 调用方取消不回滚已接受的原生命令；迟到回复不能把另一个属性查询完成为 `null` 或异常，也不能发布为新的媒体/会话故障 |
| 已提交请求超时，迟到成功/错误 | 超时释放普通播放修改的等待，后续查询及修改可完成；迟到回复按原请求关联隔离 |

这 7 项在请求行为未修改时全部通过；受控测试没有复现所怀疑的取消清理窗口，因此不宣称修复了取消竞态，也未改动请求调度。

仅为缩短超时测试，在内部构造函数增加可选请求超时参数；相关测试使用 **250 毫秒**。默认请求超时仍为 **15 秒**，初始化等待仍为 **15 秒**，后端等待媒体加载完成仍为 **20 秒**。

上述限制属于各自等待阶段，不是包含恢复租约、修改锁和加载步骤的总耗时上限。修改锁等待支持调用方取消，本轮未添加独立的 15 秒期限；已提交操作超时或取消也不等于向 core 发出撤销。

## 5. 真实媒体归属证据

`BackendMediaIdentityTests` 增加两项真实会话场景：

1. A、B 两次加载分别进入本机 HTTP 服务后取消调用方等待，C 已实际发起请求但其响应仍受屏障阻塞时，才放行 A/B 的旧响应。C 的加载不能提前成功；最终后端地址、原生 `path`、时长和音轨均属于 C。
2. 在 backend 订阅之前拦住一次真实 `StartFile` 的送达，取消旧加载等待并请求下一媒体。事件线程尚未消费完旧 Start 时，下一次解除暂停请求不能获得回复并继续提交 `loadfile`；放行后验证最终媒体一致。

第二项只延迟消费真实事件，没有生成或调换 StartFile；它验证这个消费屏障，不能证明 mpv 内部所有旧 Start/End/属性重排均被排除。本轮未引入媒体代次 ID，也未证明全部事件与加载请求可唯一对应。
